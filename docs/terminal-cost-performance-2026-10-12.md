# 终端计算成本定位与单次规划候选复用

日期：2026-10-12；基于 `main` @ `6a2e7ba` 的开发工作区。新机器设计继续冻结。

本轮在已有持续刷新基准上加入分段计时，定位到候选解析占单人多目标和大型结构规划耗时的约 94%。优化仅复用单次目标规划中的候选方块定义；每位玩家仍只接收、渲染自己的选中预览，预览和材料数据继续独立，每 10 tick 刷新，主动操作立即响应。

## 测量口径

沿用七种负载、两轮轮换顺序、20 tick 预热及安静/变化各 100 tick，前后各 28 条记录。单人覆盖 1/16 个粉碎机目标和一座默认 15×15 蓄热熔炉；2/8 人组同时保护原有隔离与错峰行为。变化组修改真实世界方块和各自背包，多目标组在中途主动切换目标。

同一 Windows 11 AMD64、Zulu Java 17.0.13、Python 3.12.7 环境，11 份测量输入中只有规划器指纹不同；计时器、夹具、基准、刷新调度、快照、构建配置均一致。基线运行完成后才改为优化源码，不用模拟旧逻辑代替真实基线。

`stages` 记录每阶段调用次数、总耗时、100 tick 的 P95 和最大值。`refresh` 包括周期检查及同刻主动全量操作；`preview` 包含规划、需求汇总和材料查询，`plan` 包含 `candidates`。这些是包围计时，不能相加。`candidates.calls` 表示真实候选列表解析次数，复用命中不计为新解析。材料阶段包含背包与可选 AE 查询，本基准关闭 AE。

END 和 START→END 是事件区间，包含其他监听器，不能当作完整服务器 MSPT。接收解码检查在 END 计时外执行；模拟连接没有 TCP、压缩或客户端渲染。未测真实 AE 网络、客户端 FPS或堆分配字节；两轮样本不作跨平台性能保证，耗时不设自动门禁阈值。

```bash
python tools/benchmark_terminal_preview.py --mode refresh --offline --label baseline
python tools/benchmark_terminal_preview.py --mode refresh --offline --label optimized
```

## 优化边界

候选解析继续调用 GTCEu 的公共 `SimplePredicate.getCandidates()`，过滤、去重及顺序保持原样。每次 `plan()` 新建按谓词身份索引的临时表，返回的格子、放置项和候选摘要仍复制堆叠。临时表不保存玩家、世界状态、工程配置、预览格或材料数量，也不跨目标/请求存活。分层与全局数量上限、指定配额、线圈/信道选择及当前方块状态仍按原规则逐格计算。施工启动和实际操作继续独立规划与实时校验。

计时只在 `gse.refreshBenchmark=true` 且测量作用域开启时记录；普通运行不读取时钟或创建样本。记录只含线程内计时/次数数组，END 完成和夹具清理时移除，不保存任何玩家内容。网络协议仍为 7，施工预算仍为 32 方块/刻；客户端渲染、持有/离线生命周期和会话相位未改动。
