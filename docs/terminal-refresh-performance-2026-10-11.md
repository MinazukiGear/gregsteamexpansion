# 终端持续刷新压测与错峰更新（2026-10-11）

本轮将终端独立会话分散到十个 tick 相位，保持每人每 `10 tick` 实时检查、主动操作立即响应和按玩家 UUID 隔离的工程、预览与材料。第二轮八人各持有 16 个目标、世界和背包持续变化时，服务端 END 事件区间 P95 从 `1,561.1 ms` 降至 `224.2 ms`，最大区间从 `1,725.0 ms` 降至 `251.9 ms`；同一 tick 的包峰值从 8 降至 2。该场景 100 tick 的 END 区间总和仍约为 `15.9 s`：错峰主要分散集中峰值，单份昂贵预览仍需后续优化。

## 负载与测量口径

通过 `tools/benchmark_terminal_preview.py --mode refresh` 在独立世界中放置已有蒸汽粉碎机和默认 `15×15` 蓄热熔炉。粉碎机覆盖 1/2/8 位模拟生存玩家、每人 1/16 个目标的六种负载，另测一人单熔炉。七种负载轮换顺序测两轮；每组预热 20 tick，然后分别测安静状态和变化状态各 100 tick，共 28 条记录。变化状态每 tick 改变每人的独立库存，每 20 tick 放置或拆除一个普通蓝图方块；多目标组在中途主动切换一人的选中目标。

压测使用真实 `UltimateTerminalEvents → UltimateTerminalMessages.tick` 刷新、差异比较及包编码路径。模拟接收连接逐份解码全量/增量包，核对各自目标、修订号以及选中和批量材料的独立背包数量。解码验证在下一次测试回调中执行，先于库存变化，且位于 END 计时区间之外。AE 关闭，模拟连接没有 TCP、压缩和客户端渲染。

END 区间从高优先级 END 监听器量到低优先级 END 监听器，包含普通优先级的终端事件与其他监听器，并非纯预览 CPU 时间。START→END 事件区间还包含夹具、验证和其他服务器工作，也不是完整服务器 MSPT。所有分位数按各组 100 个 tick 计算；基线十次集中刷新使 P50 接近零，错峰后的 P50 上升是工作分散的结果。未测客户端 FPS、真实多人网络、堆分配或真实 AE 网络的刷新性能；两轮本机样本不作为跨平台性能保证。

复现命令（JDK 17）：

```bash
python tools/benchmark_terminal_preview.py --mode refresh --offline --label baseline
python tools/benchmark_terminal_preview.py --mode refresh --offline --label optimized
```

`--label` 只标记报告，不切换源码；复现前后比较须分别使用基线刷新实现和优化实现。普通回归、重启和依赖冒烟不注册该基准命名空间，耗时没有硬性通过阈值。

## 隔离与剩余边界

生产代码仅调整会话刷新调度：会话仍按 UUID 保存各自快照，每次规划实时读取本人的工程、世界和材料，并只向本人连接发送。客户端继续只渲染本机玩家当前选中目标的预览。没有增加跨请求或跨玩家预览/材料缓存，网络协议仍为 `7`，施工调度和全服施工额度不变。

新增普通 GameTest 以八份不同目标和不同库存核对独立全量/增量包、八个刷新相位、世界改变后的材料需求、收起和重新持有、离线清理与重连、主动请求只影响本人及原会话周期保持。持续刷新基准的两次 28 条记录也全部通过接收隔离检查。

本机完整门禁 `python tools/verify.py --offline` 通过，日志为 `.tmp/terminal-refresh-full-gate.log`：

- 普通回归、双 JVM 重启的写入/核验、Easy/Normal/Expert 配置重启，共六轮各 `193/193` 项必需 GameTest 通过，均包含新增刷新生命周期测试；配置检查恢复原配置。
- 仅必需前置、AE2、完整依赖三种隔离运行各 `1/1` 项冒烟通过。
- 9 项可移植性工具负向夹具、编译、datagen 一致性、92 个生成资产、语言键、设计契约、获取路线、经济与构建门禁通过。
- JAR 审计检查 425 个 Java 17 类和 429 个资源；设计统计为 193 项普通测试、24 项终端测试，历史性能和发布记录保留当时统计。

## 候选源码 CI 的夹具修正

首次推送候选源码 `eb7ddbe` 的[四平台 CI](https://github.com/MinazukiGear/gregsteamexpansion/actions/runs/38138927386)在 macOS arm64 重启写入阶段报告 `steam_air_intake_collects_while_unformed` 未完成采集，在 Windows arm64 的 Easy 配置阶段报告 `air_intake_alone_starts_air_batch` 未检测到启动。此前本机完整门禁通过，两个失败来自已有空气链路测试，需要处理后重新核验候选源码。

独立进气测试现在把入口朝东放在自身模板内并明确清空入口格，在原有 100 tick 超时内观察首批实际采集，再保留精确 `2,000 mB`、NBT 存储、外部能力关闭和 Jade 去重断言。离心机测试明确设置朝外入口，按 `SteamSupplyHatchPartMachine` 类型注入蒸汽，避免部件遍历顺序把蒸汽写入普通流体仓；在原有 400 tick 超时内等待真实采集和首次启动，并核对启动配方为 `gtceu:centrifuge/air_separation`。空气仍完全由真实入口采集，没有手动注入空气。失败诊断补充入口朝向和前方方块。机器生产逻辑、终端刷新代码和基准的十份测量输入均未改动，测试数量仍为 `193`。

两处修正共同通过本机重启核验阶段的 `193/193` 项回归和 `build` 审计，记录为 `.tmp/terminal-refresh-ci-fix-validation.log`。四平台门禁结果按最新提交关联的 Actions 运行核验，不用旧提交的通过记录代替。

仍需单独测量真实 AE 网络、真实客户端全息 FPS 和正式安装环境。单个多目标或大型结构仍可超过 50 ms，后续应围绕单人规划、材料统计和差异比较的成本继续定位，保持玩家隔离、状态新鲜度和施工前实时校验。新机器设计按使用者指令继续冻结。
